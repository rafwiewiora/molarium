                                                    Abstract

          Commercial computational drug-discovery software has traditionally bundled three sources of value:
      the interface, the scientific models, and the specialized expertise required to operate those models and
      translate their outputs into design decisions. Large language models, coding agents, and tool-using
      scientific agents are beginning to unbundle this paradigm. Interfaces, analyses, workflow logic, and
      substantial portions of scientific software can increasingly be generated around a particular scientist,
      project, and question, while agents can automate sophisticated workflows that previously required
      specialist users.
          We argue that this does not commoditize computational drug discovery itself. It shifts the locus of
      differentiation. Faster execution does not improve an inaccurate model, extend an applicability domain,
      or make a weak prediction more useful. As the tool layer becomes cheaper and more fluid, competitive
      advantage should increasingly accrue to better and more generalizable models, proprietary experimental
      data, accumulated discovery intelligence, and the human judgment required to know what to ask and
      what to believe.
          Molarium, available at https://molarium.org, provides a case study of this transition. Developed
      over an intensive weekend by a drug-discovery scientist working with a coding agent, this free open-
      source molecular workbench runs primarily in a standard web browser and combines local molecular
      visualization, editing, conformer search, molecular mechanics, molecular dynamics, machine-learned
      potentials, and protein-structure prediction. More importantly, Molarium preserves a versioned molecular
      state, user actions, method identity, provenance, and validation evidence beneath an interface that can
      change rapidly. This separation between fluid software and stable scientific state suggests a broader
      architecture for generated adaptive software in drug discovery.

Keywords: agentic software development; computational chemistry; molecular design; WebGPU; scientific
validation; provenance; discovery intelligence


1    From fixed software products to generated adaptive software
Successful computational drug discovery depends on applying the right method at the right time, with
appropriate settings, assumptions, and scientific context. Historically, this has been a tedious, error-prone,
and often poorly reproducible process confined to a relatively small number of computational specialists.
Docking requires careful protein preparation, protocol selection, appropriate constraints, and critical
evaluation of the resulting poses before they can inform design. Molecular dynamics adds requirements
for system preparation, force-field assignment, simulation protocols, compute infrastructure, trajectory
analysis, and visualization, while free-energy calculations introduce further complexity in perturbation

design, sampling, convergence assessment, and alignment with experimental conditions. Similar layers of
infrastructure surround cheminformatics, quantum chemistry, property prediction, molecular generation,
and structural modeling.
Commercial scientific software has created considerable value by simplifying and integrating many of these
activities. Graphical interfaces reduced technical barriers, workflow engines connected otherwise fragmented
programs, and software packages encoded operational details needed to apply methods consistently. The
same integration, however, coupled scientific questions to relatively fixed software environments. Project-
specific improvements competed with broader product roadmaps, new analyses often required engineering
support, and scientific users frequently adapted their questions to the capabilities and conventions of the
available applications rather than the reverse.
Large language models and coding agents are beginning to change this relationship. A scientist with deep
drug-discovery expertise but limited programming experience can increasingly describe an application,
analysis, visualization, or workflow in natural language and have software constructed around the scientific
need. Tool-using agents extend this capability by operating established methods, linking calculations,
handling routine failures, and assembling results into forms that support decisions. Chemistry systems
such as ChemCrow, ChemGraph, and related agentic frameworks demonstrate that language models can
increasingly coordinate external tools and computational workflows rather than merely discuss them [1–4].
The consequence is not simply faster software development. It is a change in how drug hunters can interact
with computational science. Rather than learning and adapting to a fixed software environment, scientists
can increasingly shape the software around the question, the stage of the project, the data available at that
moment, and their own preferred way of reasoning about the problem. A medicinal chemist optimizing a
macrocycle need not use the same interface as a structural biologist interrogating a cryptic pocket or a
program team deciding which compound to advance. The interface can become a temporary and adaptive
view over a more durable scientific substrate.
Molarium emerged from this model. It began as a request for a better environment in which to inspect and
manipulate molecular structures and expanded through use. Scientific objections became software changes:
an implausible geometry triggered a change in molecular editing semantics; an unexpected energy led
to an explicit numerical reference; ambiguity about a computational backend forced the implementation
to expose which engine was actually running; and unsupported methods were converted into explicit
limitations rather than hidden assumptions. The application evolved while the scientific question was still
active.


2    Molarium and the value of a persistent molecular state
Molarium is an MIT-licensed, local-first molecular viewer, builder, and simulation workbench. Most
supported calculations execute on the user’s device using WebAssembly or WebGPU, allowing molecular
graphics, editing, cheminformatics, conformer exploration, molecular mechanics, molecular dynamics,
machine-learned potentials, and selected protein-structure prediction workflows to coexist in a standard
browser environment. The browser is important because it collapses installation and orchestration overhead
and, for supported calculations, can avoid remote job submission, cloud compute charges, and application
licensing simply to remain inside the design loop. WebAssembly provides a route for mature compiled
scientific libraries to run locally, while WebGPU exposes modern accelerators through a portable browser
API [5, 6].

This becomes particularly important when interfaces themselves are inexpensive to modify. If every
generated view is free to redefine a molecule, select a different charge model, change protonation, alter
preparation, or reinterpret a trajectory, flexibility becomes a source of scientific ambiguity. Generated
adaptive software therefore demands a more explicit boundary between presentation and scientific state
than fixed software typically provides.
Molarium takes this principle further by retaining the sequence of molecular states and user actions that
produced the current session. Edits, selections, manipulations, calculations, and other interactions form an
event history rather than leaving only the final molecular coordinates. The resulting architecture is closer
to version control than to a traditional molecular project file. A molecular state can be associated with
the actions that produced it, the calculation applied to it, and the evidence available at that point in the
design process.
The analogy to “Git for molecules” is useful, although the scientific object is richer than source code. A
drug-design trajectory contains not only structural changes but also changing hypotheses, model outputs,
uncertainty, and experimental evidence. In a discovery setting, such a history could preserve which analogs
were considered, which structures or properties influenced a design, which alternatives were rejected, and
what was learned when a compound was eventually synthesized and tested. This creates a foundation for
recording medicinal-chemistry design trajectories rather than merely storing the compounds that survived
them. Much of the most valuable information in a discovery program lies in the path not taken, yet
conventional databases usually preserve only endpoints.
The browser also provides a useful trust boundary for proprietary work. Molarium’s Local Lab mode can
restrict network access and verify reviewed application assets, while supported calculations remain on the
local device. Because privacy controls depend on deployment configuration, this architecture makes data
movement explicit and auditable. Organizations can therefore evaluate and enforce how molecular data
are handled rather than treating data transfer as an invisible property of a remote software stack.

3    Scientific contracts: provenance, validation, and falsifiability
Cheap, adaptive software creates a new scientific risk. An agentically generated workflow is most impactful
and most liable precisely when it fills gaps fluently enough that the user no longer notices where the
scientific contract ended. If a new analysis view can be created in minutes, that view must still expose
which molecule, model, parameters, assumptions, and evidence produced the result. Otherwise, reducing
the cost of software generation merely increases the rate at which scientific ambiguity can be created.
We therefore use the term scientific contract to describe the set of invariants and evidence that give
a computational result meaning. A molecular mechanics result is not defined by the label “molecular
mechanics.” It depends on the molecular state, parameterization, charge assignment, energy function,
treatment of nonbonded interactions, constraints, boundary conditions, precision, integrator, and numerical
implementation. A learned potential depends on its architecture, weights, supported chemistry, prepro-
cessing, and training domain. A protein-structure prediction depends on the checkpoint, sequence and
template information, inference protocol, and other model-specific choices. The interface may be fluid, but
these scientific identities cannot be allowed to drift silently.
Molarium therefore keeps computational routes distinct even when they appear in the same workbench.
RDKit provides chemical perception and conformer generation; OpenFF Sage defines a molecular-mechanics
model; OpenMM Reference provides an independent numerical route for selected validation tests; STORMM-
inspired WebGPU code advances homogeneous replicas; ANI-2x provides a separate machine-learned
potential with a defined chemical domain; and OpenFold provides a separate protein-prediction model
[7–12]. These methods can be compared, chained, or presented together, but the interface does not erase
the fact that they make different approximations and answer different questions.
The same principle applies to workflow provenance. Scientific workflow research has long emphasized that
reproducibility requires retaining the data, computational process, execution environment, and provenance
that produced a result [15, 17]. More recent work formalizes workflow invariants and testable reproducibility
criteria rather than treating provenance as passive metadata [16]. Generated adaptive software increases
the importance of this idea because the workflow itself may no longer be a stable artifact defined months
before execution. It can be created or modified during the scientific interaction.
This leads to a stronger requirement: generation of a scientific workflow should be accompanied by
generation of the conditions under which its claims could be falsified. If an agent implements a new
conformer-search strategy, the output should include not only the workflow but also the benchmark that
would test whether it improves conformational coverage, the reference needed to evaluate it, the tolerance
that defines agreement, and the cases that lie outside the intended scope. If an agent adds a numerical

When software is difficult to construct, implementation effort can obscure the distinction between building

4    Local computation changes the interaction model
The claim presented here is not that a web browser should replace production molecular simulation software
or high-performance computing. Current native GPU codes remain substantially more capable for large

periodic systems, long trajectories, specialized force fields, advanced sampling, and many other demanding
workflows. Molarium itself remains deliberately bounded, and several of its browser-native routes are
experimental.
The more consequential observation is that a standard browser on commodity personal hardware can
now host molecular calculations of sufficient sophistication to change the interaction model between
scientist, software, and discovery team. Workflows that previously required separate installations, specialist
environments, remote compute submission, substantial orchestration, or commercial applications can
increasingly occur within the active design session. For supported workloads, the result, method identity,
assumptions, validation evidence, and molecular history remain attached to the same scientific state rather
than being fragmented across files, programs, notebooks, and job systems.
This has implications for both latency and economics. A scientist can interrogate a structure, modify a
molecule, launch a local calculation, compare alternative models, and inspect the result without leaving
the design environment. The marginal cost of many small calculations approaches the cost of the local
hardware already present on the desk, rather than incurring a remote orchestration cycle or per-calculation
cloud charge. An open-source workbench also removes application licensing as the gatekeeper to these
supported workflows. These advantages are most important for calculations that sit directly in the design
loop, where minutes of friction repeated hundreds of times can matter more than the peak performance of
an isolated benchmark.
Local execution also changes the distribution of control. The scientist can determine which analysis should
exist, how data should be juxtaposed, and which calculation should be available at the point of decision.
Molarium itself is evidence of this change: a scientist did not need to wait for every useful workflow to
appear on a conventional product roadmap. Missing interfaces and bounded implementations could be
added while the underlying question was still active.
The important caveat is that lower latency increases the need for scientific discipline. Cheap execution can
tempt users to run more calculations simply because they are available. The goal is not maximal computa-
tional throughput; it is maximal scientific leverage. The useful question is whether a calculation changes
a design decision, reduces meaningful uncertainty, or identifies an experiment that would discriminate
among competing hypotheses.

5    What becomes scarce when the tool layer becomes cheap
Molarium helps separate three layers of value that have historically been packaged together. The first is
the tool layer: graphical interfaces, visualization, format conversion, wrappers, workflow logic, reports,
job control, data plumbing, and bounded numerical implementation. These capabilities remain important
and require maintenance, but their marginal reproduction cost is falling quickly as coding agents improve.
A scientist can increasingly generate a project-specific view or connect an existing computational method
without waiting for the corresponding feature to become part of a commercial release.
The second is the model layer: force fields, quantum mechanical methods, docking and scoring functions,
free-energy models, machine-learned potentials, protein-structure predictors, molecular representations,
property models, parameterization, weights, uncertainty calibration, and the experimental evidence that
defines their useful domain. This layer does not become inexpensive simply because invocation becomes
easier. A docking model with an inadequate scoring function remains inadequate when invoked by an
agent. A force field with a systematic error becomes more dangerous, not less, if an automated workflow
generates thousands of confident predictions from it. A machine-learned property model does not acquire
extrapolative validity because a language model describes its answer fluently. A protein-structure predictor
does not become reliable for a particular conformational state because it is available through a better
interface.
As the mechanics of invoking a model become less scarce, differences among models become more important.
Easier access does not improve predictive quality, and obtaining poor answers faster may save human time
while doing little to increase the probability of success. This distinction is particularly important in drug
discovery, where the objective is frequently to extrapolate into new chemistry, new structural states, and
new biological contexts rather than interpolate within a well-sampled training distribution [18–20].
The third layer is discovery intelligence: proprietary experimental data, negative results, project history,
assay context, structural interpretation, design rationale, internal protocols, expert judgment, program
objectives, and the remembered reasons that apparently attractive ideas failed. Molarium intentionally
contains little of this third layer because it is a public workbench built primarily from public scientific
components. That absence clarifies the opportunity. An organization could build generated adaptive
interfaces over the same architectural principles while connecting them to internal structures, assay data,
pharmacokinetics, target biology, medicinal-chemistry reasoning, and program objectives.

The versioned molecular history described above creates an important bridge into this third layer. Tradi-

to preserve this decision trajectory. Over repeated design cycles, the organization can accumulate not only
data but the relationship between hypotheses, interventions, predictions, decisions, and outcomes.
This is more than provenance in the narrow sense of reproducing a calculation. It is decision provenance.
A future system should be able to answer not only “How was this free-energy value computed?” but
also “Why was this molecule proposed?”, “Which alternatives were rejected?”, “What evidence changed
the team’s view?”, and “Which prediction ultimately proved useful or misleading?” That information is
difficult to reconstruct retrospectively and highly specific to an organization’s science. It may therefore
become one of the most durable forms of discovery intelligence.
Agentic systems provide a mechanism to operationalize this knowledge. A protein-preparation skill can
encode how an organization treats protonation, crystallographic waters, alternate conformations, unusual
residues, and escalation of ambiguous cases. A free-energy skill can encode accepted transformations,
convergence criteria, diagnostics, and failure modes. A compound-design skill can combine measured and
predicted properties with uncertainty, synthetic feasibility, novelty, and current program objectives. The
important asset is not the prose of the prompt; it is the versioned decision process, including its inputs,
models, assumptions, controls, domain restrictions, escalation conditions, and accountable scientific owner.


6    The changing role of scientific expertise
There is an apparent paradox in this transition. As software becomes easier to construct and operate,
human judgment becomes more important. Traditional computational expertise includes substantial
operational knowledge: how to prepare a particular input, which menu exposes a setting, how to translate
files between programs, how to recover a failed job, or how to reproduce a standard analysis. These skills
remain useful, but an increasing fraction can be encoded in software and agents. The broader automation
literature has long recognized that reducing routine operation can increase the importance of human
expertise precisely when the system encounters ambiguous or abnormal conditions [21].
The highest-value expertise therefore shifts toward selecting the right question, deciding the appropriate
level of model fidelity, defining the acceptable tradeoff among speed, throughput, and accuracy, recognizing
implausible results, choosing meaningful controls, and determining which result would actually influence a
project decision. This is a different emphasis from learning how to operate conventional scientific software.
The scientist closest to the underlying discovery problem—whether a medicinal chemist, structural biologist,
mechanistic biologist, pharmacologist, or computational scientist—can increasingly interact directly with
the relevant data and calculations rather than requiring every question to pass through a software
intermediary.
We do not view this as the disappearance of computational scientists. The more plausible outcome is a
shift in leverage. Less specialist time needs to be spent constructing repetitive interfaces, transferring files,
or manually operating routine workflows. More can be spent on model development, molecular physics,
parameterization, sampling, uncertainty, validation, and difficult edge cases where the established workflow
fails. Once that expertise is made explicit, part of it can be encoded into reusable scientific skills that
broaden access without pretending that the underlying science has become simple.
Molarium’s development illustrates the division of labor. The coding agent could inspect a repository,
refactor software, implement numerical kernels, add tests, and repeat the loop rapidly. The scientist had to
decide which result looked chemically impossible, whether a reference was genuinely independent, whether
a discrepancy mattered, and what evidence would change belief. The agent compressed the distance
between recognizing a scientific need and changing the software; it did not remove the need to recognize
the scientific need.
The bottleneck therefore shifts from operation toward epistemology. What approximation is acceptable?
What is the appropriate tradeoff between cost and fidelity? Which result deserves an independent control?
Is the reference actually independent? Is a model being used outside its applicability domain? What

and decision history more important, not less. The scarce assets shift from operating software toward

Molarium also suggests that molecular design environments should preserve more than the latest structure.
A versioned record of molecular states, user actions, calculations, assumptions, and results can capture the
trajectory by which scientific decisions were made. Coupled to explicit scientific contracts and falsification
tests, that history can make generated adaptive software not only easier to build, but more reproducible,
extensible, and scientifically accountable.
When software is difficult to construct, implementation effort can hide the distinction between building a
method and validating it. When implementation becomes easy, the remaining scientific obligations become
much harder to ignore. The opportunity is therefore not simply to generate more software. It is to put
adaptable computational capability directly in the hands of the scientists who understand the problem,
while preserving the models, evidence, and decision history that determine whether the answer should be
trusted.
